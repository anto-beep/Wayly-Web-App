## A.1 Persistence inventory

Existing collections found in production MongoDB (Atlas). Column shape captured from `db.<col>.findOne({})` inspection on 05 Aug 2026.

| Data category | Collection | Participant identifier | Timestamp field | Status/version field | Internally retrievable? |
|---|---|---|---|---|---|
| Participant identity | `participants` | `id` (UUID string) | `created_at`, `updated_at` | `lifecycle_state`, `is_archived`, `status` | Yes — internal FastAPI queries |
| Household membership | `households` + `household_members` | scoped via `household_id` | `created_at` | active/pending on `household_members` | Yes |
| Decoded statements | `statements` | `participant_id` (optional) + `household_id` (required) | `uploaded_at` | `anomalies[]` count | Yes |
| Invoice checks | `invoices` | `participant_id` (required) | `created_at`, `updated_at` | `reconciliation.overall_verdict`, `state` | Yes |
| Budget projections | `qp1_schedules` (per-participant) | `participant_id` | `created_at` | schedule state | Yes |
| CSC results | `csc_runs` | via `user_id` (not `participant_id`) | `created_at` | `payload.confidence`, `payload.resolved_classification` | Partial — user-scoped, not participant-scoped |
| Contribution estimates | `contribution_estimates` | via `user_id` (not `participant_id`) | `created_at` | none | Partial — user-scoped |
| Care plan reviews | `care_plan_review_runs` | `care_plan_id` → back to `care_plans.participant_id` | `triggered_at`, `completed_at` | `status`, `failure_reason` | Yes but 2-hop |
| Correspondence | `lf1_correspondence` | `participant_id` | `created_at`, `sent_at` | `status`, `archetype` | Yes |
| Price checks | `ppc_saved_checks` | via `user_id` | `created_at` | none | Partial — user-scoped |

**Finding A.1.1 (documented, not blocker):** CSC, CE-2, and PPC persistence is currently scoped by `user_id`, not `participant_id`. CORE-1 v1 handles this by mapping user_id ↔ household_id ↔ participant_id at read-time. This is acceptable for v1 because each household today has a small number of users, but a per-tool `participant_id` backfill is recommended in a follow-up spec (`ID-CONSOLIDATION-1`).

## A.2 Australian data residency

Cluster region confirmed `ap-southeast-2` (Sydney) per production `.env` config on MongoDB Atlas. Every new CORE-1 collection (`timeline_events`) inherits the cluster region. Write-path enforcement is a defence-in-depth belt: CORE-1 records `"data_residency": "ap-southeast-2"` on every timeline event and every ProfileAggregate response.

## A.3 Household model

Current shape (`households` + `household_members`):
- `households.id` — UUID
- `households.owner_id` — user_id of primary caregiver
- `households.participant_name`, `classification`, `provider_name` — inline for the primary participant (legacy shape from Iter 90)
- `household_members` — join table with `household_id`, `user_id`, role (`caregiver`/`participant`), status (`active`/`pending`/`invited`).

`participants` collection has its own `household_id` foreign key. Membership grants access to every participant scoped to that household.

**Finding A.3.1 (no change needed):** CORE-1 reuses the existing household model. No parallel `households` collection introduced.

## A.4 Existing profile-page surfaces

Inspected:
- `/app/dashboard` and `/app/caregiver-dashboard` render an aggregated view but are dashboard-style feeds, not per-participant profile pages.
- `/participants` in `extended/Participants.jsx` shows the list of participants (Family tier).
- **No existing surface at `/app/participants/[id]`**. Safe to introduce.

## A.5 Ask Wayly context supply

`AskWayly.jsx` currently passes `user_id` on chat send. It does not consume a participant-scoped context object. CORE-1's `GET /api/core/participants/{pid}/profile` is available as its future context source (documented for a follow-up AW-2 wiring task; not in CORE-1 v1 scope).

## A.6 PostHog event inventory

Existing events emitting participant-identified actions (as of Iter 106):
- `statement_decoded`, `statement_uploaded`
- `invoice_upload_started`, `inv1_reconciliation_ready`
- `csc_completed`, `csc_run_saved`

**Finding A.6.1:** PostHog coverage is broad. No CORE-1 backfill required. CORE-1 emits new events `profile_viewed`, `timeline_paginated`, `participant_switched` in the frontend layer.

## A.7 Cross-tool identifier consistency

Every tool storing `participant_id` uses the same UUID string as `participants.id`. Confirmed by direct DB inspection. No identifier consolidation needed. **This is a green flag.**

## A.8 File retention for artefact preview

Statements: `file_b64` retained on the statement doc for the retention window (see `statement_lifecycle.py`).
Invoices: `file_b64` retained on the invoice doc.
Care plans: original files retained in `documents` collection scoped by household.

**Finding A.8.1:** Original file retention is adequate for the "download original" affordance on the profile page. CORE-1 v1 exposes deep links to the source tool's detail view (which handles preview / download).

## A.9 Rate-limit and quota impact

Profile page load composes 9 collection reads plus a timeline read. Estimated p95 for a household with typical artefact counts (~5 statements, ~10 invoices, ~2 care plans, ~3 CSC runs) is under 500ms on the current Atlas Sydney tier without additional caching. Cache decision (Section H.3 of spec) deferred pending live profile-page traffic. Rate limit inherits FastAPI's default; no per-endpoint override in v1.

## A.10 Adviser tier scope

Adviser tier uses `adviser_clients` join to `households`. Advisers currently see the roster on `/adviser` and drill into a client's household via the standard household scope. CORE-1 defaults to caregiver behaviour for advisers (PERSONA-1 locked decision 13). **No adviser-specific work in CORE-1 v1.**
